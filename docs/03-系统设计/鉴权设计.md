# 鉴权设计

## 背景

平台不支持传统注册登录，采用 **HttpOnly Cookie + RLS** 方案实现无感鉴权：
- 用户首次访问时，middleware 自动分配 `device_id`（UUID v4）
- `device_id` 存储在 HttpOnly cookie 中，客户端 JS 无法读取或篡改
- 所有 API 请求自动携带 cookie，服务端从 cookie 中提取身份
- Supabase RLS 策略基于 `x-device-id` 请求头实现行级权限控制

---

## 架构总览

```
浏览器                        Next.js Server                    Supabase
  │                               │                               │
  │  GET / (首次访问)              │                               │
  │ ─────────────────────────────>│                               │
  │                               │ middleware:                    │
  │                               │   无 device_id cookie          │
  │                               │   → 生成 UUID, 设为 HttpOnly   │
  │ <─────────────────────────────│   Set-Cookie: device_id=xxx   │
  │                               │                               │
  │  POST /api/favorites          │                               │
  │  Cookie: device_id=xxx ──────>│ route handler:                │
  │                               │   从 cookie 读取 device_id     │
  │                               │   传入 createClient(deviceId)  │
  │                               │   → header: x-device-id=xxx ─>│
  │                               │                               │
  │                               │                  RLS:          │
  │                               │                  device_id =   │
  │                               │                  get_device_id()│
  │                               │                               │
```

## 核心组件

### 1. Middleware（`src/middleware.ts`）

- 首次访问时生成 `device_id` UUID，写入 HttpOnly cookie
- Cookie 属性：`httpOnly=true`, `secure`（生产环境）, `sameSite=lax`, `maxAge=1年`
- 同时处理城市路由重定向逻辑

### 2. Auth 工具（`src/utils/auth.ts`）

```typescript
getDeviceIdFromCookie(request)  // 从 NextRequest 的 cookie 中提取 device_id
requireDeviceId(request)         // 提取并校验，缺失则返回 401
```

### 3. Supabase 服务端客户端（`src/utils/supabase/server.ts`）

```typescript
createClient(deviceId?: string)
```

- 接受可选 `deviceId` 参数
- 通过 `global.headers` 将 `x-device-id` 注入到每个 Supabase 请求中
- RLS 策略通过 `get_device_id()` 函数读取此 header

### 4. SQL 函数（`schema.sql`）

```sql
CREATE OR REPLACE FUNCTION public.get_device_id()
RETURNS TEXT
LANGUAGE sql STABLE
AS $$
  SELECT nullif(current_setting('request.headers', true)::json->>'x-device-id', '');
$$;
```

## RLS 策略

### listings 表

| 操作 | 策略 | 说明 |
|------|------|------|
| SELECT | `USING (true)` | 所有人可读 |
| INSERT | `WITH CHECK (true)` | 所有人可发布 |
| UPDATE | `USING (sellerDeviceId = get_device_id() OR sellerDeviceId IS NULL)` | 仅卖家可改价/编辑 |

### favorites 表

| 操作 | 策略 | 说明 |
|------|------|------|
| SELECT | `USING (device_id = get_device_id())` | 仅可查看自己的收藏 |
| INSERT | `WITH CHECK (device_id = get_device_id())` | 仅可添加自己的收藏 |
| DELETE | `USING (device_id = get_device_id())` | 仅可删除自己的收藏 |

### notifications 表

| 操作 | 策略 | 说明 |
|------|------|------|
| SELECT | `USING (device_id = get_device_id())` | 仅可查看自己的通知 |
| INSERT | `WITH CHECK (true)` | 任何人可发通知（联系卖家场景：买家通知卖家） |
| UPDATE | `USING (device_id = get_device_id())` | 仅可更新自己的通知 |
| DELETE | `USING (device_id = get_device_id())` | 仅可删除自己的通知 |

## API 层双重校验

除了 RLS，API 路由还做了应用层校验：

1. **通知 PATCH/DELETE**：cookie 中的 `device_id` 必须与请求体中的 `device_id` 一致，否则 403
2. **商品 PATCH（降价）**：先查询 `sellerDeviceId`，与 cookie `device_id` 比对，非 owner 返回 403
3. **收藏 POST/DELETE**：cookie `device_id` 必须与请求体 `device_id` 一致

## 联系卖家流程

买家联系卖家时，通知需要发送给**卖家**而非买家：

```
1. 买家在 ListingDetail 点击"联系卖家"
2. 前端从 listing.sellerDeviceId 获取卖家的 device_id
3. POST /api/notifications { device_id: 卖家的sellerDeviceId, ... }
4. 卖家在 /me?tab=messages 中看到通知
5. 卖家同意/拒绝 → PATCH /api/notifications
```

`sellerDeviceId` 在发布商品时由 PostListing 组件写入 listing 记录，来源为当前用户的 cookie `device_id`。

## 迁移指南

如果之前使用旧的 localStorage `device_id`：

1. 部署新代码后，middleware 会在首次请求时自动创建 HttpOnly cookie
2. `AppContext.getOrCreateDeviceId()` 优先从 cookie 读取，回退到 localStorage
3. 旧 localStorage 中的 `device_id` 仍可作为 fallback，但不再作为可信来源
4. 建议在 Supabase SQL Editor 中执行最新 `schema.sql` 更新 RLS 策略
